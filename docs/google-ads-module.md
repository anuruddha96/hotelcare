# Google Ads native module — approved Phase 1 + Phase 2

This milestone replaces session-only Google authorization with organization-scoped, server-side offline authorization and read-only ingestion. It does not implement Phase 3 venue mapping or any campaign mutation.

## Production prerequisites (do not skip)

- Google Cloud project: HotelCare; Google Ads API enabled and Explorer access approved (2,880 production operations per rolling 24 hours). Use OAuth credentials belonging to that same project. v26 project-based API authorization: https://developers.google.com/google-ads/api/docs/api-policy/developer-token
- Configure a dedicated Google Ads Web application OAuth client in the existing Cloud project. This avoids disrupting Gmail or Google Business Profile authorizations. Add scope https://www.googleapis.com/auth/adwords, openid and email. Complete OAuth consent and verification as required; externally published apps in Testing can receive short-lived refresh tokens. See https://developers.google.com/google-ads/api/docs/oauth/multi-user-authentication and https://developers.google.com/google-ads/api/docs/productionize/secure-credentials.
- Add the exact authorized redirect URI https://hotelcare.app/rdhotels/google-ads in the client. For each additional organization pilot, register https://hotelcare.app/<organization-slug>/google-ads. The callback is restricted to that organization's authenticated administrator and origin; no caller-supplied redirect URL. No separate browser Google OAuth script is necessary.
- Configure Edge Function secrets in the HotelCare Supabase project: GOOGLE_ADS_CLIENT_ID, GOOGLE_ADS_CLIENT_SECRET, GOOGLE_ADS_TOKEN_KEY (base64 encoding of exactly 32 random bytes), GOOGLE_ADS_WORKER_SECRET (separate high-entropy secret, at least 32 characters). Never put secrets into the repository, chat, logs, browser storage or client bundles. Keep a secure backup of the encryption key; losing it requires reconnecting accounts. Key rotation requires an explicit migration or reauthorization.
- After CI and security review, apply the Phase 2 migration, deploy google-ads-report with gateway verify_jwt=false (user actions independently verify a JWT with auth.getUser and check database role and tenant; worker actions require its separate private secret), and publish frontend.
- Provision Vault entries google_ads_worker_url = https://pcmszqqklkolvvlabohq.supabase.co/functions/v1/google-ads-report and google_ads_worker_secret = the same worker secret stored in Edge secrets. Create these using the protected dashboard or authorized secret provisioning process, not a plaintext committed SQL script. The scheduler is installed only where pg_cron, pg_net and Vault exist; it performs no HTTP requests unless both Vault entries are present. Verify job registration and logs after deployment.
- Sign in as an administrator of the intended organization, connect each Google identity, explicitly enable only the advertising accounts belonging to that organization, and verify an initial synchronized report. The initial import is bounded by the job queue and quota.

## Security model

- The OAuth authorization code is exchanged server-side using PKCE S256 and one-use, ten-minute state tied to the authenticated user and organization. Stored state is hashed. The UI strips callback parameters after capture. No browser access/refresh tokens are used. Only the server can access the AES-256-GCM encrypted refresh token (bound to organization UUID and verified Google subject). Refresh happens as needed; invalid grants mark the connection expired.
- All Google Ads tables have RLS enabled, no public/authenticated/anon access, and explicitly restricted service-role-only grants. All new RPCs are security invoker with explicit execute grants. Edge routes require a fresh authenticated administrator in their own active organization; no client-supplied organization UUID or raw GAQL. Explicit account selection gates ingestion and report access.
- Multiple Google identities per organization are supported. Manager accounts are expanded to client accounts and the correct login-customer-id is stored. One active ingestion source per customer per organization; duplicate sources must be disabled before another can be enabled. An unavailable account is not synchronized. Partial discovery does not mark unvisited accounts unavailable.
- Disconnect deletes the stored refresh token and stops jobs and cached-report access for the connection. It intentionally does not revoke the Google grant globally because the same identity/client could serve another explicitly authorized organization; users may revoke access in their Google account if desired. Previously ingested historical data is retained under the organization's service-only storage.
- Administrator-only pilot remains until Phase 3 venue permissions are separately approved. No Google Ads writes are exposed.

## Sync and reporting semantics

- A worker runs once per minute and claims one due account using row locking and a bounded lease. Account hierarchy refresh has a separate daily lease and a 10-minute worker trigger. Each enabled account targets today's metrics and current budgets hourly, a recent 7-day window every six hours, previous 30 days daily and 90 days weekly for attribution restatements. These are targets, not guaranteed deadlines under quota, API errors or very large portfolios. Backfill processes 30-day chunks to a maximum lookback of 730 days (about 24 months); historical coverage is explicitly recorded even for successful empty results. All failed or incomplete reports leave coverage and data unchanged; exponential backoff and quota errors are visible.
- A rolling 24-hour project-wide operation ledger reserves conservatively for each Google Ads HTTP call (including pagination and failed calls). Sync cap 1,728; interactive cap 576; total 2,304. Remaining 576 of the approved 2,880 reserved for future management/emergency use. This is a conservative internal budget, not Google's own accounting, and does not count unrelated clients sharing the Cloud project.
- A single transaction replaces the complete fetched date window, preserving uniqueness by account/day/campaign. Cached analytics reads use one SQL statement for consistency and distinguish incomplete date coverage from verified zero metrics. Current campaign settings and enabled budgets are refreshed; budget changes are captured intraday. Current daily budgets are deduplicated by resource ID. No mixed-currency totals. Google Ads conversions/values are not actual PMS revenue.
- Mira receives only a user-triggered bounded numerical snapshot when the selected report range is fully covered. Direct Mira tool access, venue mapping, campaign management and autonomous changes remain out of scope until later approval.

## Testing / release gates

1. Frontend CI (full test suite, production build) and Google Ads Phase 2 CI (isolated PostgreSQL 17 migration/integration fixture and Deno typecheck) must pass.
2. Verify production schema grants, RLS, function privileges and cron registration after migration. Test signed-out and non-admin requests; tenant mismatch; reconnect; expired/replayed state; manual account selection; wrong worker secret; no leakage of OAuth secrets.
3. Real Google authorization must be completed by an authorized Google user; verify the Ads scope, grant refresh, MCC discovery, current and historical GAQL reports, account currency/time zone, budgets and selected-date spend/impressions/clicks/conversions against Google Ads UI.
4. Verify scheduled job execution, status/coverage, retries, disconnect behavior and quota usage. Do not mark the phase complete or proceed to Phase 3 until live smoke tests pass. No production secrets are supplied by this PR.
