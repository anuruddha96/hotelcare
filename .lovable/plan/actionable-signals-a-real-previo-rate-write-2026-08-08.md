# Actionable signals + a real Previo rate write

## 1. Quick signals become actions people can close

Today "Quick signals from today's sales" is a list of read-only sentences computed in the browser (`TodaysSalesAdrGoal.tsx`, the `recommendations` memo). Nothing records that a revenue manager acted on one.

What changes:

- Each signal gets **Mark done**, **Dismiss** and a one-line "what I did" note. A done signal stays visible for the rest of the day with who closed it and when, then moves into history.
- Signals get a stable identity (hotel + date + signal kind + subject, e.g. "raise rates · 2026-10-30") so the same signal is not re-served after it was closed, and so the same signal reappearing next week can be traced.
- Actions are stored, not just hidden: hotel, signal, decision (done / dismissed / ignored-by-expiry), note, user, timestamps, plus the numbers the signal was based on. That is the data set for later "did acting on this signal help?" analysis, and it is fed back to the AI as context ("this hotel usually dismisses channel-mix signals").
- A small footer line shows the day's tally: acted on X of Y signals.

## 2. Signals generated by your own OpenAI account, at top intelligence

The heuristics stay as an instant fallback, but the displayed signals come from a new backend call:

- New edge function `revenue-signals` calls **OpenAI directly with your `OPENAI_API_KEY`** (the same secret the other revenue functions already use — not the Lovable gateway), on OpenAI's strongest reasoning model, with reasoning effort set high.
- It is given the real numbers, never asked to invent them: today's bookings with channel, room type, rate, stay date and lead time; ADR/goal pace; pickup per stay date; demand grades and events already recorded; the current price and the minimum ADR; and the recent history of which signals this hotel acted on or dismissed.
- It must return strict structured output — each signal with a title, the evidence sentence, the affected dates/room types, a suggested price move, a confidence, and an urgency. Anything without evidence in the supplied data is rejected before it is shown.
- Signals that carry a price move get an **Apply as draft** button, so acting on a signal creates the same rate draft the Demand pricing panel creates, and pushing it goes through the normal Review & push bar.
- Results are cached per hotel per ~15 minutes so the page does not re-bill a heavy model on every render, with a manual "Re-analyse" control.

## 3. Rates that actually reach Previo

The current write path guesses: `_shared/previoRateWrite.ts` walks a list of candidate method names (`setRates`, `setRate`, `setPrices`, `setPrice`, `updateRates`) with a hand-shaped body. That is the placeholder behaviour and the reason pushes fail.

What changes:

1. **Confirm the real call against your live account first.** Using the hotel's stored Previo hotel ID and secret key, run the documented Previo rate/availability write for one date, one room type, at its current price, and capture the verbatim response. That single result decides the exact method name, payload shape and auth variant — and whether the account carries the write scope at all. Everything after this step is written against the confirmed call, not against a candidate list.
2. **Delete the candidate loop and the invented XML** once the real shape is known, and replace it with the documented request built from the hotel's own identifiers: Previo hotel ID from `pms_configurations.pms_hotel_id`, credentials from that hotel's own secret, rate plan and room type from `previo_rate_plan_mapping`, date, occupancy, price and currency from the draft. Multi-account tenants (SLNT) resolve credentials per PMS account, so a draft is never sent to the wrong property.
3. **Prove each push.** After the write, re-read the same date/room type/occupancy and compare; a draft is only marked pushed when Previo reports the new price back. Mismatch or rejection keeps the draft with Previo's verbatim message so it can be retried.
4. **Say the truth in the UI.** If the account genuinely lacks rate-write scope, the push dialog shows Previo's own words plus the exact text to send Previo support, instead of a generic "non-2xx status code".

## Technical notes

- Rewrite `supabase/functions/_shared/previoRateWrite.ts` around one confirmed method; keep `readPrevioRate` for verification. `revenue-push-drafts` and `previo-rate-write-probe` both use it; the probe becomes a diagnostics tool rather than the discovery mechanism.
- Credential resolution moves to the per-account helper used by `previo-revenue-sync` so portfolio hotels pick the right hotId/secret pair.
- New table `revenue_signal_actions` (hotel, signal key, signal payload snapshot, decision, note, user, created_at) with hotel-scoped access, plus `revenue_signal_runs` for the cached AI output.
- New edge function `revenue-signals` (OpenAI direct, `OPENAI_API_KEY`, strict JSON schema, evidence validation, action history in the prompt).
- `TodaysSalesAdrGoal.tsx` renders AI signals with per-signal action controls and falls back to the local heuristics if the call fails or credits run out.
